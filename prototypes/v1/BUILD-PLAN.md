# Build Plan — prototypes/v1

## Scope
Prototype แรกของ AI Disease Surveillance & Response Platform โฟกัสที่ **Outbreak Dashboard** เพียงหน้าเดียว ระดับ "Full Analytics Dashboard" (ยังไม่มี Requirement/Backlog/Feature List/User Journey อย่างเป็นทางการ — ผู้ใช้เลือก scope นี้จาก 3 ทางเลือกที่เสนอ)

## หน้าที่สร้าง
- **`index.html` — Outbreak Dashboard (หน้าเดียว, เป็นหน้าหลักของ v1)**
  - Top navigation bar: wordmark "AI-DSRP", ชื่อหน้า "Outbreak Dashboard", เมนูอื่น (Cases, Alerts, Reports) แสดงเป็น placeholder/disabled เพราะยังไม่อยู่ใน scope รอบนี้
  - KPI cards แถวบน: Total Active Cases, New Cases Today, Active Outbreak Zones, Overall Risk Level
  - Panel แผนที่ความเสี่ยงตามภูมิภาค: ใช้ region grid แบบง่าย (ภาคเหนือ/กลาง/อีสาน/ใต้/ตะวันออก/ตะวันตก — 6 ภาค) ระบายสีตามระดับความเสี่ยง แทนแผนที่จริงจาก map tile (เพื่อให้เปิดออฟไลน์ได้ ไม่พึ่ง CDN)
  - กราฟแนวโน้มเคสตามช่วงเวลา (14 วันล่าสุด) วาดด้วย inline SVG
  - รายการแจ้งเตือนล่าสุด (Recent Alerts) พร้อม severity badge (warning/danger) และ timestamp/พื้นที่
  - Filter (โรค, ภูมิภาค, ช่วงวันที่) — UI ใช้งานได้จริงกับ mock data ในหน้า (กรอง client-side ด้วย JS)

## Backlog/Feature ที่ไม่รวมในรอบนี้
- หน้า Case Reporting Flow, Alert & Response Management แบบเต็ม, ระบบ login/สิทธิ์ผู้ใช้, การเชื่อมต่อ backend จริง — เมนูใน nav bar เตรียมไว้เป็น placeholder สำหรับต่อยอดในเวอร์ชันถัดไป

## Assumption ที่ตั้งไว้
- ข้อมูลทั้งหมดเป็น mock data สมมติบริบทประเทศไทย (ภาค/จังหวัดตัวอย่าง)
- แผนที่แสดงผลแบบ region grid อย่างง่าย ไม่ใช่แผนที่ภูมิศาสตร์จริง

## Version
`prototypes/v1` — รันครั้งแรก ไม่มี version เดิมให้เลือก

## เพิ่มเติม 2026-08-20 — หน้า Case Intake (การรวบรวมข้อมูล โรงพยาบาล → เทศบาล)

### Requirement ต้นทาง
ปัญหา: ข้อมูลรายงานโรคจากโรงพยาบาลอยู่ในรูป PDF/JPEG จำนวนมาก ต้องแปลงเป็น Google Sheet + เก็บไฟล์ต้นฉบับไว้ลงรับหนังสือ แนวทางที่ผู้ใช้เสนอ: OCR/AI extraction ดึงข้อมูล (ชื่อ, HN, ที่อยู่, วันป่วย, ผลตรวจ) เข้า Google Sheet อัตโนมัติ, เก็บไฟล์ต้นฉบับคู่กับแถวข้อมูลใน Google Drive, แจ้งเตือนทีมสอบสวนโรค 5 หน่วยผ่าน LINE OA ตามพื้นที่ตำบล/หมู่บ้าน, และ generate spot map + รัศมี 100 เมตรจากพิกัด/Geocoding

### Scope
เพิ่มหน้าใหม่ `case-intake.html` เข้าไปใน `prototypes/v1` เดิม (แก้ของเดิมในที่ ไม่สร้าง v2) โดยเปิดใช้เมนู "Cases" ใน left rail (จาก placeholder disabled เดิม) ให้ชี้มาหน้านี้ — ไม่แตะ `index.html` (Outbreak Dashboard)

### โครงสร้างหน้า (single-page dashboard รวมทุก step ของ pipeline)
1. **Upload panel** — mock drag-drop สำหรับ PDF/JPEG พร้อมรายการไฟล์ที่อัปโหลดล่าสุด (sample data)
2. **ตารางตรวจสอบผล OCR** — แถวข้อมูลที่ AI ดึงมา (ชื่อ, HN, ที่อยู่, ตำบล/หมู่บ้าน, วันป่วย, ผลตรวจ) พร้อมสถานะ "รอตรวจสอบ" / "ยืนยันแล้ว" มีปุ่ม **ยืนยัน** ต่อแถว (human-in-the-loop ก่อน auto-route) แต่ละแถวมีลิงก์ "ไฟล์ต้นฉบับ" (mock, เสมือนลิงก์ Google Drive)
3. **Notification log** — เมื่อยืนยันแถวแล้ว แสดง log การแจ้งเตือนไปยัง 5 ทีมสอบสวนโรค (เขต 1-5) พร้อม timestamp และสถานะ "ส่งแล้ว"
4. **Spot map panel** — ต่อยอด region-grid SVG แบบเดียวกับ `index.html` แต่ zoom ระดับตำบล/หมู่บ้าน แสดงหมุดเคสที่ยืนยันแล้ว + วงรัศมี 100 เมตร พร้อม badge "ปรับพิกัดด้วยมือ" สำหรับเคสที่ geocode แม่นยำต่ำ (toggle สถานะได้ด้วย JS ไม่ใช่ drag จริง)

### Backlog/Feature ที่ไม่รวมในรอบนี้
การเชื่อมต่อ Google Sheet/Drive/LINE OA จริง, OCR/Geocoding API จริง, drag-and-drop map จริง — ทั้งหมด mock ด้วย client-side JS/sample data

### Assumption ที่ตั้งไว้
- ชื่อทีมสอบสวนโรคใช้ mock: "ทีมสอบสวนโรค เขต 1" ถึง "เขต 5"
- ข้อมูลตัวอย่างเป็นบริบทไทย
- แผนที่แบบ abstract grid/SVG (สอดคล้องกับ assumption เดิมของ index.html ที่ไม่พึ่ง map tile/CDN)
- Human-in-the-loop: แถวข้อมูลต้องกด "ยืนยัน" ก่อนจึงจะขึ้น notification log และปักหมุดบนแผนที่ (ไม่ auto-route ทันทีที่ OCR เสร็จ)

### Version
แก้ไข `prototypes/v1` เดิมในที่ (เพิ่มไฟล์ `case-intake.html` ใหม่ ไม่แตะ `index.html`)

### Design Reference
อ้างอิง `DESIGN.md` ฉบับ Earth Tone + Minimalist + Muji เดิม ให้เข้าชุดกับ `index.html`

## เพิ่มเติม 2026-08-20 (รอบ 2) — แก้ไขข้อมูลในตาราง OCR ก่อนยืนยัน/แจ้งเตือน

### Requirement ต้นทาง
ผู้ใช้ต้องการให้แก้ไขข้อมูลที่ OCR ดึงมาผิดพลาดได้ ก่อนกด "ยืนยัน" (ก่อนระบบส่งแจ้งเตือนไปยังทีมสอบสวนโรค) — เพราะถ้ายืนยันไปทั้งที่ข้อมูลผิด (เช่น ตำบลผิด) จะ auto-route เคสไปผิดทีม

### Scope
แก้ไข `prototypes/v1/case-intake.html`, `case-intake.js`, `styles.css` ในที่ (ไม่สร้าง v2) — เพิ่มปุ่ม **"แก้ไข"** ต่อแถวในตาราง OCR Review (เฉพาะแถวที่ยังไม่ยืนยัน) กดแล้วเซลล์ในแถวนั้น (ชื่อ-สกุล, HN, ที่อยู่, ตำบล-หมู่บ้าน, วันป่วย, ผลตรวจ) กลายเป็น input แก้ไขได้แบบ inline ในตาราง พร้อมปุ่ม **"บันทึก"** / **"ยกเลิก"** — บันทึกแล้วข้อมูลแถวนั้นอัปเดต (รวมถึงทีมที่จะ auto-route ถ้าตำบล/หมู่บ้านเปลี่ยน) ก่อนที่จะกด "ยืนยัน" ส่งแจ้งเตือนต่อ

### Backlog/Feature ที่ไม่รวมในรอบนี้
แก้ไขแถวที่ยืนยันแล้ว (ต้อง unlock ก่อนถึงจะแก้ได้ — ยังไม่อยู่ใน scope นี้), การ sync กลับไปยัง Google Sheet จริง

### Assumption ที่ตั้งไว้
- แก้ไขได้เฉพาะแถวสถานะ "รอตรวจสอบ" เท่านั้น
- ถ้าแก้ "ตำบล/หมู่บ้าน" แล้วระบบจะ map ทีมสอบสวนโรคที่รับผิดชอบใหม่ตามค่าที่แก้ (ถ้าตรงกับ pattern ที่ระบบรู้จัก) เพื่อให้ auto-route ถูกต้องตามข้อมูลที่แก้ไขแล้ว

### Version
แก้ไข `prototypes/v1` เดิมในที่ (ไม่สร้าง v2)

### Design Reference
อ้างอิง `DESIGN.md` เดิม — input แก้ไขใน table ใช้ style เดียวกับ Input/Form guideline ข้อ 3 (label บนไม่จำเป็นในบริบท inline table แต่ border/focus state ต้องตรงตาม pattern เดิม)

## เพิ่มเติม 2026-08-20 (รอบ 4) — หน้า Control Plan และ Field Tracking (ทีมควบคุมโรค/ทีมพ่น)

### Requirement ต้นทาง
Pain point ข้อ 3 จาก [ROADMAP.md](./../../ROADMAP.md) Phase 3 — ทีมควบคุมโรค (ทีมพ่น) ต้องการ: (1) auto-generate ใบขออนุมัติเบิกน้ำมัน/น้ำยาเคมี, (2) AI ร่างแผนปฏิบัติงานควบคุมโรค, (3) real-time tracking ทีมพ่นเทียบกับ spot map ที่วางแผนไว้, (4) AI vision ตรวจสอบรูปถ่ายภาคสนามว่าตรงพื้นที่/เวลาจริงไหม

### Scope
เพิ่ม 2 หน้าใหม่เข้าไปใน `prototypes/v1` เดิม (แก้ของเดิมในที่ ไม่สร้าง v2) พร้อมเพิ่มเมนู **"Control Plan"** และ **"Field Tracking"** ใน left rail ต่อจาก "Case Analysis" — ไม่แตะ "Alerts"/"Reports" ที่จองไว้สำหรับ phase อื่น

### โครงสร้างหน้าที่ 1 — `control-plan.html`
1. **ร่างใบขออนุมัติเบิกน้ำมัน/น้ำยาเคมี** — เลือกพื้นที่/cluster (reuse cluster ที่ยืนยันแล้วจาก case-analysis.js ถ้าเป็นไปได้ หรือ mock ชุดใหม่ที่สอดคล้องกัน) → generate เอกสารร่างจากข้อมูล (พื้นที่, จำนวนหลังคาเรือน, รัศมี) ในกล่องแก้ไขได้ พร้อมปุ่ม "ส่งขออนุมัติ" (mock เปลี่ยนสถานะรออนุมัติ → อนุมัติแล้ว)
2. **ร่างแผนปฏิบัติงานควบคุมโรค** — generate แผนปฏิบัติงาน (ทีมที่มอบหมาย, วันที่ปฏิบัติงาน, ขั้นตอน) ในกล่องแก้ไขได้ พร้อมปุ่มยืนยันใช้งานแผน

### โครงสร้างหน้าที่ 2 — `field-tracking.html`
1. **Real-time tracking ทีมพ่น** — ต่อยอด spot map SVG แบบเดียวกับ case-intake.js/case-analysis.js แสดงตำแหน่ง/โซนของทีมพ่นแต่ละทีม พร้อมสีสถานะ (ยังไม่ถึง/กำลังพ่น/พ่นแล้ว) เทียบกับโซนที่วางแผนไว้ — mock เพราะ LINE ไม่มี continuous location API จริง (ตาม ROADMAP.md Phase 3)
2. **AI vision QC รูปถ่ายภาคสนาม** — กริดการ์ดตัวแทนรูปภาพ (ใช้ icon/placeholder เพราะไม่มีไฟล์รูปจริง ไม่ใช้ภาพประกอบตกแต่งตาม DESIGN.md ข้อ 7) พร้อม badge ผลตรวจ (พิกัดตรง/ไม่ตรง, เวลาตรง/ไม่ตรง) — mock เพราะรูปจาก LINE มักถูกล้าง EXIF ออก (ตาม ROADMAP.md Phase 3)

### Backlog/Feature ที่ไม่รวมในรอบนี้
AI drafting/tracking/vision จริง, การเชื่อมต่อ backend/LINE จริง — ทั้งหมด mock ตาม Phase 3 ใน ROADMAP.md

### Assumption ที่ตั้งไว้

## เพิ่มเติม 2026-08-21 (รอบ 17) — สถานะพ่นแล้ว (Day 0/1/7) + ซ่อนรายการที่พ่นครบแล้วออกจากตารางแผนปฏิบัติงาน

### Requirement ต้นทาง
ในตาราง "ร่างแผนปฏิบัติงานควบคุมโรค" ผู้ใช้ต้องการ:
1. แสดงเฉพาะรายการที่ยังไม่ได้พ่นควบคุมโรค — รายการที่พ่นครบทั้ง Day 0, Day 1 และ Day 7 แล้ว (ครบทั้ง 3 วัน) ให้ซ่อนออกจากตาราง
2. รายการที่พ่นไปแล้วบางส่วน (เช่น Day 0 หรือ Day 1 เสร็จแล้ว) แต่ยัง**ไม่ครบ Day 7** ให้ยังคงแสดงอยู่ (ค้างไว้ ยังไม่ซ่อน)
3. ต้องมีช่องให้เลือก/ทำเครื่องหมายว่าพ่นวันไหนไปแล้วบ้าง (Day 0 / Day 1 / Day 7 ต่อรายการ)

หมายเหตุ: หลังรอบ 16 หนึ่งเคสอาจมี 2 pool item (ที่อยู่ + ที่ทำงาน) แยกกัน ดังนั้นสถานะพ่นแล้วต้องผูกกับ **pool item key** (เช่น `"1-home"`/`"1-work"`) ไม่ใช่ผูกกับ `area.id` เฉยๆ เพื่อให้ที่อยู่กับที่ทำงานของเคสเดียวกันมีสถานะพ่นเป็นอิสระต่อกัน

### Scope
แก้ไข `prototypes/v1/control-plan.html`, `control-plan.js`, `styles.css` ในที่ (ไม่สร้าง v2) — จำกัดเฉพาะส่วน "ร่างแผนปฏิบัติงานควบคุมโรค" (ตาราง `#workplan-schedule-table` และข้อความสรุปที่เกี่ยวข้อง) เท่านั้น **ไม่แตะ** ส่วน "ร่างใบขออนุมัติเบิกน้ำมัน/น้ำยาเคมี" (area-select-list, แท็บที่อยู่/ที่ทำงาน, มินิแมป) — รายการยังคงแสดงครบในส่วนนั้นเหมือนเดิมไม่ว่าจะพ่นครบหรือยัง เพราะผู้ใช้ระบุเจาะจงถึงเฉพาะส่วนแผนปฏิบัติงานเท่านั้น

### รายละเอียด
1. **เพิ่ม state ใหม่**: `sprayDoneByKey` (object, key = pool item `key` เดิม เช่น `"1-home"`, value = `{0: boolean, 1: boolean, 7: boolean}`, default ทุกรายการเป็น `false` ทั้ง 3 วัน) — แยกจาก `workplanEntryByKey` เดิม (ซึ่งเก็บ team/dayOffset/hour/minute ของ "การพ่นที่กำลังจะทำ" ไม่ใช่ประวัติว่าพ่นวันไหนไปแล้วบ้าง)
2. **เพิ่มคอลัมน์ใหม่ในตาราง** (คอลัมน์ที่ 5 ต่อจาก "เวลาเริ่ม"): "สถานะพ่นแล้ว" แสดง 3 checkbox ต่อแถว พร้อม label สั้นๆ "Day 0" / "Day 1" / "Day 7" (`<label>`+`<input type="checkbox">` ปกติ) ผูกกับ `sprayDoneByKey[poolItem.key][0|1|7]` — ติ๊กแล้วอัปเดต state ทันทีและ re-render ตาราง (`renderWorkplanSchedule()`)
3. **Filter การแสดงผลแถว**: ในลูป render ของ `renderWorkplanSchedule()`/`getSortedWorkplanRows()` ให้ข้ามแถวที่ `sprayDoneByKey[poolItem.key]` มีค่า `true` ครบทั้ง 3 คีย์ (0, 1, และ 7) — ไม่ต้องสร้าง `<tr>` ให้แถวนั้น แถวที่พ่นไปบางวัน (1 หรือ 2 ใน 3) แต่ยังไม่ครบ ให้แสดงตามปกติ
4. **Empty state ใหม่**: ถ้าทุกแถวถูกซ่อนหมด (พ่นครบทุกรายการแล้ว) ให้แสดงข้อความในตาราง เช่น "ทุกรายการพ่นควบคุมโรคครบ Day 0/1/7 แล้ว ไม่มีรายการที่ต้องดำเนินการเพิ่มเติม" แทนแถวว่างเปล่า
5. **ข้อความสรุปเหนือ/ใต้ตาราง** — เพิ่ม/ปรับข้อความให้บอกจำนวนที่ซ่อนไปด้วยความโปร่งใส เช่น "(ซ่อน {M} รายการที่พ่นครบ Day 0/1/7 แล้ว)" เมื่อ M > 0

7. ตัวควบคุมเดิมทั้งหมด (team select, dayOffset select "วันพ่นถัดไป", hour/minute select, การจัดกลุ่ม/เรียงลำดับตามทีม, ตัวกรองวันครบกำหนดพ่นจากรอบ 14-15, การเปิดใช้ 2 ตำแหน่งต่อเคสจากรอบ 16) คงเดิมทุกอย่าง ทำงานเฉพาะกับแถวที่ยังแสดงอยู่ (ยังไม่ถูกซ่อน)

ผู้ใช้ขอให้ "จัดการได้เลย" ต่อจากข้อเสนอในรอบ 18 ที่ระบุว่า sourceFile เป็น mock ใหม่ ไม่ได้จับคู่ตรงกับ `case-intake.js` แบบ 1:1 — ตรวจสอบพบว่า `AREAS[3]` (id 4, ต.เกาะแก้ว หมู่ 5 บ้านหาดทราย) มี `clusterRef` ระบุชัดว่า "เคสไข้เลือดออกยืนยันใหม่ (จาก Case Intake)" และตรงกับ `case-intake.js` → `CASES[5]` (id 6) ทุกจุด: subdistrict "เกาะแก้ว", village "บ้านหาดทราย", villageNo "5", labResult ไข้เลือดออก (Dengue NS1) — เป็นคู่ที่ตั้งใจให้เชื่อมกันมาแต่ต้นแต่ patientName/houseNo/sourceFile ไม่ตรงกันจริง (เพราะแต่ละรอบก่อนหน้าเติม mock เองแยกกัน)

### Scope
แก้ไข `prototypes/v1/control-plan.js` เฉพาะ `AREAS[3]` (id 4) เท่านั้น — ไม่แตะ `case-intake.js` และไม่แตะเคสอื่น (id 1-3)

### รายละเอียด
1. `patientName`: `"นายประเสริฐ แสงทอง"` → `"นางสาวละออ แสงจันทร์"` (ตรงกับ `CASES[5].patientName` "ละออ แสงจันทร์" ในไฟล์ case-intake.js เป๊ะ ๆ เติมคำนำหน้า "นางสาว" ให้สอดคล้องกับ pattern คำนำหน้าที่ใช้กับเคสอื่นในไฟล์นี้ เพราะ case-intake.js ไม่มีคำนำหน้าเก็บไว้)
2. `locations[0].houseNo`: `"23"` → `"21"` (ตรงกับ `CASES[5].houseNo`)
3. `locations[0].address`: `"ต.เกาะแก้ว หมู่ 5 บ้านหาดทราย"` → `"ต.เกาะแก้ว หมู่ 5 บ้านหาดทราย อ.เมือง จ.สงขลา"` (เติม อำเภอ/จังหวัดจาก `CASES[5].district`/`.province` ให้ครบเหมือนต้นฉบับ)
4. `sourceFile`: `"รพ.สต.เกาะแก้ว_dengue_59027.pdf"` (mock รอบ 18) → `"รพ.สต.เกาะแก้ว_dengue_58890.pdf"` (ค่าจริงจาก `CASES[5].fileName`)

### Backlog/Feature ที่ไม่รวมในรอบนี้
เคส id 1-3 ไม่มีคู่ที่ตรงกันแบบ 1:1 ใน `case-intake.js` ชัดเจนพอ (ชื่อ/พื้นที่/โรคชี้ไปคนละทิศทางกัน — เช่น patientName "กิตติ มั่นคง" ตรงกับ Area 1 แต่ subdistrict+โรคตรงกับ Area 3 มากกว่า) จึงไม่บังคับจับคู่ในรอบนี้ เพื่อไม่ให้เกิดการเชื่อมที่ผิด/สร้างความสับสน — ยังคง `sourceFile` แบบ mock ตามรอบ 18 ไว้เหมือนเดิมสำหรับ 3 เคสนี้ — ไม่แก้ `caseFoundDate` ของเคส id 4 (เป็น field คนละความหมายจาก `onsetDate`/`uploadedLabel` ของ case-intake.js ไม่บังคับให้ตรงกัน)

### Assumption ที่ตั้งไว้
- คำนำหน้าชื่อ "นางสาว" สำหรับ "ละออ แสงจันทร์" เป็นการเติมเองให้สอดคล้องกับ pattern คำนำหน้าของเคสอื่นในไฟล์นี้ เพราะ `case-intake.js` ไม่ได้เก็บคำนำหน้าไว้ ไม่ทราบสถานภาพจริง
- เคส id 1-3 จงใจไม่จับคู่ในรอบนี้ตามเหตุผลข้างต้น — ถ้าผู้ใช้ต้องการให้จับคู่แบบเจาะจง (เช่น ยึดชื่อเป็นหลักหรือยึดพื้นที่+โรคเป็นหลัก) ต้องสอบถามเพิ่มก่อนแก้ เพราะทั้ง 2 เกณฑ์ชี้ไปคนละเคสกัน

### Version
แก้ไข `prototypes/v1` เดิมในที่ (ไม่สร้าง v2)

### Design Reference
ไม่มีการเปลี่ยนแปลง UI/CSS ในรอบนี้ — เป็นการแก้ไขข้อมูล mock ให้ตรงกับข้อมูลจริงในไฟล์อื่นเท่านั้น

## เพิ่มเติม 2026-08-23 (รอบ 20) — Auto-scroll จากแผนปฏิบัติงานไปใบขออนุมัติน้ำมัน/น้ำยาเคมี

### Requirement ต้นทาง
ผู้ใช้ขอ 3 จุด: (1) เปลี่ยน "พื้นที่รับผิดชอบ" เป็น "ชื่อ-สกุลผู้ป่วย", (2) แถบเลือกที่อยู่/ที่ทำงานพร้อมกรอกเลขที่/สถานที่ทำงานได้จริง, (3) เมื่อร่างแผนเสร็จแล้วให้ต่อไปทำใบขออนุมัติเบิกน้ำมัน/น้ำยาเคมีได้เลย — ตรวจสอบพบว่าจุด 1-2 มีอยู่แล้วในโค้ด (uncommitted จาก session ก่อนหน้า, รอบ 13/16) จึงเหลือแค่จุด 3 ที่ต้องทำเพิ่ม สอบถามผู้ใช้แล้วเลือกแนวทาง "auto-scroll ไปส่วนใบขออนุมัติทันทีที่กดยืนยันแผน"

### Scope
แก้ไข `prototypes/v1/control-plan.html`, `control-plan.js` ในที่ (ไม่สร้าง v2)

### รายละเอียด
1. เพิ่ม `id="control-plan-approval-panel"` ให้ `<div class="panel">` ของส่วน "ร่างใบขออนุมัติเบิกน้ำมัน/น้ำยาเคมี"
2. ใน `confirmWorkplan()` หลังตั้งค่า badge "ยืนยันใช้แผนนี้แล้ว" ให้เรียก `document.getElementById("control-plan-approval-panel").scrollIntoView({behavior:"smooth", block:"start"})` เพื่อพาผู้ใช้ไปยังส่วนถัดไปทันที

### Backlog/Feature ที่ไม่รวมในรอบนี้
ไม่เพิ่มปุ่ม "ถัดไป" ใหม่, ไม่ gate/disable ส่วนใบขออนุมัติให้รอการยืนยันแผนก่อน (ยังกดทำใบขออนุมัติเองได้ทุกเมื่อเหมือนเดิม)

### Assumption ที่ตั้งไว้
- จุด 1-2 ของ requirement รอบนี้ถือว่าตรงตามที่มีอยู่แล้วจากรอบ 13/16 ไม่ต้องแก้ไขเพิ่ม

### Version
แก้ไข `prototypes/v1` เดิมในที่ (ไม่สร้าง v2) — ยืนยันจากผู้ใช้แล้ว

### Design Reference

## เพิ่มเติม 2026-08-23 (รอบ 21) — Outbreak Dashboard: ภูมิภาค (6 ภาคทั่วประเทศ) → เขตบริการ (4 เขต) + ชุมชน (63 แห่ง)

### Requirement ต้นทาง
ผู้ใช้ส่งตารางข้อมูลจริง 63 แถว ระบุโครงสร้างพื้นที่ของเทศบาล: เขตบริการ 4 เขต แต่ละเขตมีชุมชนย่อย (รวม 63 ชุมชน) และแต่ละชุมชนมี "ทีมสอบสวนโรค" (1-5) รับผิดชอบ — Outbreak Dashboard เดิมใช้ "6 ภูมิภาคของประเทศไทย" (เหนือ/กลาง/อีสาน/ใต้/ตะวันออก/ตะวันตก) เป็นมิติหลัก ซึ่งไม่สอดคล้องกับหน้าอื่นทั้งหมดในระบบที่ออกแบบมาสำหรับเทศบาลเดียว (Control Plan, Case Intake ฯลฯ) — ถือโอกาสแก้ scope ของ Dashboard ให้ตรงกับหน้าอื่นไปในตัว

### Scope
แก้ไข `prototypes/v1/index.html`, `script.js`, `styles.css` (เท่าที่จำเป็น) ในที่ (ไม่สร้าง v2 — ยืนยันจากผู้ใช้แล้ว)

### รายละเอียด
1. **เปลี่ยน `REGIONS` (6 ภาค) เป็น `ZONES`** (4 เขตบริการ) — แต่ละ zone มี `id`, `name` ("เขตบริการ 1" ถึง 4), และ `communities[]` (ชื่อชุมชน + `teamId` 1-5 ตามข้อมูลจริงที่ผู้ใช้ให้มาครบ 63 รายการ) — ใช้ชื่อทีม "ทีมสอบสวนโรค เขต N" ให้ตรงกับ convention ที่มีอยู่แล้วใน `case-intake.js`/`alerts.js` (ไม่ตั้งชื่อใหม่)
2. **`DISEASE_CONFIG.regionFactor`** เปลี่ยนเป็น keyed ด้วย zoneId (4 ค่าแทน 6 ค่าเดิม) — ปรับตัวเลข mock ให้สมเหตุสมผลเช่นเดิม (ไม่มีข้อมูลจำนวนเคสจริงระดับพื้นที่มาให้ จึงยังเป็น mock)
3. **Region Risk Grid**: เปลี่ยนเหลือ 4 cell (เขตบริการ 1-4) สีตาม risk level เดิม (ปกติ/เฝ้าระวัง/วิกฤต) — เพิ่ม **accordion**: คลิก cell แล้วขยายแสดงรายชื่อชุมชนทั้งหมดในเขตนั้น พร้อม badge ทีมสอบสวนโรคที่รับผิดชอบต่อชุมชน (เป็นข้อมูลอ้างอิงในรายการที่ขยายเท่านั้น — **ไม่มีตัวเลขเคสแยกรายชุมชัน**เพราะไม่มีข้อมูลจริงระดับนี้ คงตัวเลขไว้ที่ระดับเขตบริการเหมือนเดิม) เอาป้าย "จังหวัดศูนย์กลาง" เดิมออก (ไม่มีความหมายอีกต่อไปเมื่อทุกเขตอยู่ในเทศบาลเดียว)
4. **Filter**: dropdown "ภูมิภาค (REGION)" → "เขตบริการ (SERVICE ZONE)" ตัวเลือก "ทุกเขตบริการ" + เขต 1-4 — ไม่เพิ่ม filter ทีมสอบสวนโรคแยกต่างหาก (ทีมสอบสวนโรคเป็นข้อมูลอ้างอิงเฉยๆ ตามที่ยืนยันแล้ว)
5. **ALERTS**: แก้ 8 mock alert เดิมที่อ้างจังหวัดทั่วประเทศ (ภูเก็ต/อุบลฯ/ชลบุรี ฯลฯ) ให้อ้างอิงชุมชนจริงจาก 4 เขตบริการแทน (เลือกชุมชนที่ระบุ severity/โรคให้สมเหตุสมผลกับ zoneId ที่ผูกไว้)
6. **Traceability**: อัปเดต `FEAT-DASH-03` ใน `docs/01-requirements/01-spec/FEATURE-LIST.md` และ `FR-DASH-03` ใน `docs/03-testing/01-test-plan/v1/ACCEPTANCE-CRITERIA.md`/`TEST-PLAN.md` ให้บรรยายตรงกับโครงสร้างใหม่ (เขตบริการ/ชุมชน แทนภูมิภาค 6 ภาค) — เพราะ Test Spec เดิมอ้าง "6 ภาค" ตรงๆ

### Backlog/Feature ที่ไม่รวมในรอบนี้
ทีมสอบสวนโรคไม่เป็น filter dimension (ตามที่เลือก), ไม่ generate จำนวนเคสแยกเป็น 63 series ต่อชุมชน (ข้อมูลที่ให้มาไม่มีตัวเลขเคสระดับชุมชน)

### Assumption ที่ตั้งไว้
- จำนวนเคส mock ยังคำนวณที่ระดับเขตบริการ (4 ค่า) เหมือนเดิมที่เคยทำระดับภูมิภาค ไม่ลงรายละเอียดระดับชุมชน
- ชื่อ "เขตบริการ 1" ถึง "4" ใช้ตรงตามที่ผู้ใช้ระบุ ไม่ใส่ชื่อเทศบาลเฉพาะเจาะจง (ตาม privacy convention เดิมของ prototype ทั้งชุด)
- Alert ทั้ง 8 รายการ remap ไปยังชุมชนจริงในเขตบริการ 1-4 แทนจังหวัดทั่วประเทศเดิม ตามที่ยืนยันแล้ว

### Version
แก้ไข `prototypes/v1` เดิมในที่ (ไม่สร้าง v2) — ยืนยันจากผู้ใช้แล้ว

### Design Reference
อ้างอิง `DESIGN.md` เดิม — accordion ใหม่ reuse สี/badge/spacing pattern ที่มีอยู่แล้วในหน้านี้และหน้าอื่น (เช่น pattern ที่ Control Plan ใช้กับการ์ดที่ขยาย/ยุบได้) ไม่มี component ใหม่
