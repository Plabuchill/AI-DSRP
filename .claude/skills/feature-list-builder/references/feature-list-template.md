# Template — FEATURE-LIST.md

ใช้เป็นโครงเริ่มต้นเวลาเขียน/แก้ `docs/01-requirements/01-spec/FEATURE-LIST.md` — ยึดรูปแบบเดิมที่โปรเจกต์นี้ใช้อยู่แล้ว (ดูไฟล์จริงเพื่อดูตัวอย่างที่ครบสมบูรณ์)

---

## หัวเอกสาร

อธิบายว่ารวบรวมจาก 2 แหล่ง: Requirement (`REQUIREMENTS.md` หรือ pain point ที่ยังไม่มีเอกสารแยก) และ Product Backlog (`ROADMAP.md`) — และย้ำว่า Feature ID ในเอกสารนี้เป็นการตั้งขึ้นใหม่เพื่อ traceability, ใช้ prefix `FEAT-<โมดูล>` สำหรับฟีเจอร์ระดับหน้า/โมดูล และ `FEAT-<โมดูล>-NN` สำหรับฟีเจอร์ย่อยระดับ UI section

## สถานะ

- ✅ **Prototype แล้ว** — มี UI คลิกได้จริง
- 🔲 **Backlog** — ยังไม่ได้ทำ ระบุไว้เป็นแผนใน ROADMAP.md

## ต่อ 1 โมดูล

```markdown
## FEAT-<โมดูล> — [ชื่อโมดูล]

หน้า: `prototypes/vN/[ชื่อไฟล์].html` (ถ้ามี prototype แล้ว) · Requirement ต้นทาง: [อ้างจาก REQUIREMENTS.md Pain Point ID หรือบรรยายสั้น]

| Feature ID | ชื่อฟีเจอร์ | คำอธิบาย | สถานะ |
|---|---|---|---|
| FEAT-<โมดูล>-01 | ... | ... | ✅ หรือ 🔲 (Phase N) |
```

ถ้ามี Test Spec ของโมดูลนี้อยู่แล้ว ให้ใส่หมายเหตุอ้างอิงต่อท้ายตาราง (wikilink ไปยัง `ACCEPTANCE-CRITERIA.md`/`TEST-PLAN.md`) ตาม pattern เดิม

---

## หลักการเขียนที่ต้องยึดเสมอ

- **Feature ID ต้องไม่ซ้ำ** — เช็คกับไฟล์เดิมทั้งหมดก่อนกำหนดใหม่เสมอ
- **ทุก Feature ID ต้องโยง Phase ใน ROADMAP.md ได้** — ถ้า feature เป็น backlog ต้องระบุ `(Phase N)` กำกับสถานะ 🔲
- **ห้ามลบ Feature ID เดิมที่มีอยู่แล้ว** แม้จะดูล้าสมัย — ถ้าต้องเลิกใช้ ให้ทำเครื่องหมาย/ระบุหมายเหตุแทนการลบ เพื่อไม่ให้เอกสารอื่นที่อ้างอิง ID นั้นอยู่พังไปด้วย
- **บันทึกวันที่แก้ไขสำคัญ** เป็นหมายเหตุท้ายโมดูลที่แก้ (ตาม pattern "> อัปเดต {YYYY-MM-DD}: ..." ที่โปรเจกต์นี้ใช้อยู่แล้ว)
