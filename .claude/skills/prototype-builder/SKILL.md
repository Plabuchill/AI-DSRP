# Prototype Builder

Skill นี้เป็น **ตัวควบคุมขั้นตอน (orchestrator)** ที่รันอยู่ใน main loop เพราะทุกขั้นตอนสำคัญต้องคุยกับผู้ใช้ก่อนตัดสินใจ — ห้ามข้ามขั้นตอนใดไปเอง แม้จะดูชัดเจนในสายตาเราก็ตาม เพราะเป้าหมายคือให้ผู้ใช้ (ซึ่งอาจไม่ใช่สาย technical) ควบคุมทิศทางของ Prototype ได้ทุกจุดที่มีการตัดสินใจ

เมื่อถึงขั้นตอนสร้างไฟล์จริง (หลังแผนได้รับการยืนยันแล้ว) ให้ส่งงานต่อให้ subagent ชื่อ `prototype-builder` (ดูไฟล์ `.claude/agents/prototype-builder.md`) ทำหน้าที่ generate ไฟล์ HTML/CSS/JS จริงๆ เพื่อไม่ให้รายละเอียดของโค้ดมาพอกใน context หลัก

## ภาพรวม Workflow

```
0. รับ Input (Requirement / Backlog / Feature List / User Journey)
1. เช็ก DESIGN.md — ถ้าไม่มี ต้องสร้างก่อน (ถามผู้ใช้)
2. เช็กว่ามี prototypes/ เดิมอยู่ไหม — ถ้ามี ถามผู้ใช้ว่าจะสร้าง version ใหม่ หรือแก้ของเดิม
3. ร่าง Build Plan แล้วเสนอให้ผู้ใช้รีวิว/ยืนยัน (มีจุดไหนไม่ชัดเจน ต้องถามพร้อม 3 ทางเลือก+ข้อดีข้อเสีย)
4. เมื่อยืนยันแล้ว → เรียก subagent `prototype-builder` ให้ generate ไฟล์จริง
5. สรุปผลให้ผู้ใช้ พร้อมวิธีเปิดดู
```

---

## Step 0 — รับ Input

รับข้อมูลจากผู้ใช้ได้ 4 อย่าง โดย**ไม่จำเป็นต้องมีครบทุกอย่าง**:

- **Requirement** — ความต้องการเชิงธุรกิจ/ฟังก์ชัน (เช่น "ต้องเห็นแผนที่การระบาดแบบ real-time")
- **Backlog** — รายการงาน/เรื่องที่ต้องทำ (อาจมาเป็น list, ตาราง, หรือลิงก์ไฟล์)
- **Feature List** — รายชื่อฟีเจอร์ที่ต้องมีในหน้าจอ/ระบบ
- **User Journey** — ลำดับขั้นตอนที่ผู้ใช้แต่ละ persona เดินผ่านในระบบ

ผู้ใช้อาจส่งมาเป็นข้อความในแชท, แนบไฟล์ (.md, .docx, .xlsx, .pdf), หรือบอกแค่บางส่วน (เช่น "มีแค่ feature list" หรือ "อยากทำแค่ user journey ของเจ้าหน้าที่สาธารณสุข") — รับได้ทั้งหมด

ถ้าผู้ใช้ไม่ได้ระบุอะไรมาเลยนอกจาก "อยากได้ prototype" ให้ถามตรงๆ ว่าอยากโฟกัสที่ฟีเจอร์/หน้าจอ/flow ไหนเป็นอันดับแรก อย่าพยายามเดาเอง เพราะ scope ของ prototype ที่ผิดจะทำให้เสียเวลาสร้างของที่ผู้ใช้ไม่ต้องการ

ถ้าข้อมูลที่ได้มามีจุดที่ตีความได้หลายแบบ (เช่น requirement บอกว่า "แจ้งเตือนเมื่อเคสเกิน threshold" แต่ไม่บอกว่า threshold เท่าไหร่ หรือแจ้งเตือนแบบไหน) **ให้บันทึกไว้เป็นประเด็นที่ต้องถามในขั้นตอน Ambiguity (ดูด้านล่าง) ไม่ต้องถามทันทีทีละจุด** — รวบรวมแล้วถามพร้อมกันตอนเสนอแผนจะลื่นไหลกว่า

## Step 1 — ตรวจสอบ DESIGN.md (Design System ต้องมาก่อนเสมอ)

Prototype ทุกอันต้องอ้างอิงจาก `DESIGN.md` ที่ root ของโปรเจกต์ เพื่อให้หน้าตาของทุก version สอดคล้องกัน ไม่ใช่ต่างคนต่างสไตล์ในแต่ละรอบที่สร้าง

1. ตรวจว่ามีไฟล์ `DESIGN.md` อยู่ที่ root ของโปรเจกต์หรือไม่
2. **ถ้ามีอยู่แล้ว** — อ่านและใช้เป็นแหล่งอ้างอิงสีสัน/ฟอนต์/สไตล์ทั้งหมด ไปต่อ Step 2 ได้เลย โดยไม่ต้องถามซ้ำ
3. **ถ้ายังไม่มี** — ต้องหยุดตรงนี้ก่อน (ห้ามเดาโทนสีเอง หรือใช้ default generic ไปพลางๆ เพราะจะต้องรื้อสร้างใหม่ทีหลังถ้าไม่ตรงกับแบรนด์) แล้วถามผู้ใช้ว่าต้องการช่วยสร้าง DESIGN.md อย่างไร โดยเสนอทางเลือกเช่น:
   - ส่งภาพตัวอย่าง/โลโก้/เว็บที่ชอบสไตล์มาให้ดูเป็นแรงบันดาลใจ
   - บอกโทนสีหลัก (เช่น "โทนสีฟ้า-เขียว น่าเชื่อถือแบบหน่วยงานสาธารณสุข" หรือ hex code ตรงๆ)
   - บอกสไตล์ที่ต้องการ (เช่น minimal/clean, corporate/formal, friendly/rounded, data-dense/dashboard)
   - หรือถ้าไม่มีไอเดียเลย ให้เสนอ 3 แนวทางสไตล์ตัวอย่างพร้อมข้อดีข้อเสีย (ดูรูปแบบใน `references/design-system-template.md`) ให้ผู้ใช้เลือก
4. เมื่อได้ข้อมูลพอแล้ว ให้สร้าง `DESIGN.md` ตาม template ใน `references/design-system-template.md` แล้ว**ให้ผู้ใช้ยืนยันก่อน**ว่าตรงกับที่ต้องการก่อนเข้าสู่ขั้นตอนสร้าง prototype จริง (สามารถวนกลับมาปรับได้ถ้ายังไม่ตรง)

> เหตุผลที่ต้องเข้มงวดกับขั้นตอนนี้: ถ้าปล่อยให้แต่ละรอบสร้าง prototype เดายื่นสีเอง งานจะดูไม่เป็นระบบเดียวกัน และผู้ใช้ (ซึ่งมักเป็นคนที่ต้องเอาไปพรีเซนต์ต่อ) จะต้องเสียเวลาบอกซ้ำทุกรอบ

## Step 2 — ตัดสินใจเรื่อง Folder Version (ถามทุกครั้งที่เรียกซ้ำ)

Prototype ทั้งหมดเก็บอยู่ใต้โฟลเดอร์ `prototypes/` ที่ root ของโปรเจกต์ โดยแต่ละเวอร์ชันเป็นโฟลเดอร์แยกกัน:

```
prototypes/
├── v1/
│   ├── index.html ...
│   └── BUILD-PLAN.md   (แผนที่ถูกยืนยัน + requirement/backlog/feature/journey ที่ใช้ + assumption ที่ตัดสินใจไปแล้ว)
├── v2/
│   └── ...
```

ตรวจสอบก่อนว่ามีโฟลเดอร์ `prototypes/vN/` อยู่แล้วหรือไม่:

- **ไม่มีเลย (รันครั้งแรก)** — สร้าง `prototypes/v1/` ได้เลย ไม่ต้องถามเรื่อง versioning (ยังไม่มีของเดิมให้เลือก)
- **มีอยู่แล้ว (รันซ้ำ)** — **ต้องถามผู้ใช้ทุกครั้งโดยไม่มีข้อยกเว้น** ว่าต้องการ:
  1. **สร้างโฟลเดอร์เวอร์ชันใหม่** (`v{N+1}`) — คัดลอกโครงจาก version ล่าสุดมาเป็นฐาน แล้วปรับตาม request ใหม่
  2. **แก้ไขโฟลเดอร์เวอร์ชันล่าสุดโดยตรง** (`v{N}` เดิม)

ให้คำแนะนำประกอบเสมอ (ไม่ใช่แค่ถามเฉยๆ) โดยพิจารณาจากลักษณะของ request:

| แนะนำ | เหมาะกับ |
|---|---|
| **สร้าง version ใหม่** | มี requirement ใหม่ที่เปลี่ยน scope หรือ flow หลักอย่างมีนัยสำคัญ, อยากเก็บของเดิมไว้เทียบ/เดโมคู่กัน, ยังไม่แน่ใจว่า stakeholder จะชอบทิศทางใหม่หรือเปล่า (กันความเสี่ยงถ้าต้องย้อนกลับ) |
| **แก้ไขของเดิม** | เป็นการแก้ bug/ปรับเล็กน้อย, เพิ่มฟีเจอร์ย่อยที่ไม่กระทบภาพรวม, หรือแก้ตาม feedback รอบก่อนของ prototype เดิม (ไม่ใช่ direction ใหม่) |

ระบุเหตุผลสั้นๆ ตามบริบทจริงของ request นั้นๆ ให้ผู้ใช้ประกอบการตัดสินใจ แล้วรอคำตอบก่อนไปต่อ — **ห้ามเลือกให้เองโดยไม่ถาม** แม้จะดูเหมือนคำตอบชัดเจนก็ตาม เพราะผู้ใช้อาจมีเหตุผลเชิงธุรกิจ (เช่น ต้องโชว์ทั้งสอง version ให้ผู้บริหารดูคู่กัน) ที่เราไม่รู้

## Step 3 — ร่าง Build Plan แล้วเสนอให้รีวิว/ยืนยันก่อนเสมอ

**ห้าม generate ไฟล์ prototype ใดๆ ก่อนที่ผู้ใช้จะยืนยันแผนนี้** เพราะการสร้าง prototype ใช้เวลาและ token พอสมควร ถ้า scope ผิดตั้งแต่ต้นจะต้องรื้อทำใหม่

Build Plan ควรมีอย่างน้อย:

1. **Scope** — หน้าจอ/flow ไหนบ้างที่จะสร้าง (map จาก Feature List / User Journey / Backlog ที่ได้รับ)
2. **โครงสร้างหน้า** — รายชื่อหน้า/สกรีนหลัก พร้อมคำอธิบายสั้นๆ ว่าแต่ละหน้าทำอะไร เชื่อมกับ user journey step ไหน
3. **Backlog/Feature ที่รวมและไม่รวม** — ระบุชัดว่าอะไรอยู่ใน scope รอบนี้ อะไรตัดออก (และทำไม)
4. **Assumption ที่ตั้งไว้** — ถ้ามีจุดที่ไม่ชัดเจนและได้ถามผู้ใช้ไปแล้ว (ดู Ambiguity Protocol) ให้สรุปคำตอบ/decision ตรงนี้
5. **Version decision** — สร้างใหม่เป็น `vN` หรือแก้ `vN` เดิม (จาก Step 2)
6. **Design System ที่ใช้อ้างอิง** — ยืนยันว่าอ้างอิง `DESIGN.md` เวอร์ชันปัจจุบัน

เสนอแผนนี้เป็นข้อความสรุป (ไม่ต้องยาวเป็นเอกสารทางการ) แล้วรอให้ผู้ใช้ตอบรับ/ขอแก้ก่อนเสมอ ถ้าผู้ใช้ขอปรับแผน ให้ปรับแล้วเสนอใหม่จนกว่าจะยืนยัน

### Ambiguity Protocol — เมื่อมีจุดที่ไม่ชัดเจน

ทุกจุดที่ requirement/backlog/feature/journey ตีความได้มากกว่า 1 แบบ **ต้องถามผู้ใช้** โดยเสนอ**อย่างน้อย 3 แนวทาง/คำแนะนำ พร้อมข้อดี-ข้อเสียของแต่ละแนวทาง** เพื่อให้ผู้ใช้ตัดสินใจแบบมีข้อมูลประกอบ ไม่ใช่แค่ถาม "เอาแบบไหนดี" เฉยๆ

ตัวอย่างรูปแบบคำถาม:

> เรื่อง [ประเด็นที่ไม่ชัดเจน] มีแนวทางที่เป็นไปได้ดังนี้:
> 1. **[แนวทาง A]** — ข้อดี: ... / ข้อเสีย: ...
> 2. **[แนวทาง B]** — ข้อดี: ... / ข้อเสีย: ...
> 3. **[แนวทาง C]** — ข้อดี: ... / ข้อเสีย: ...
> อยากให้เลือกแบบไหน หรือมีแนวทางอื่นในใจอยู่แล้วไหม?

ใช้ `AskUserQuestion` เมื่อเหมาะสม (คำถามปิด มีตัวเลือกชัดเจน) หรือถามเป็นข้อความธรรมดาถ้าจำเป็นต้องอธิบายบริบทเยอะ รวบรวมคำถามเหล่านี้ไว้ใน Step 3 ตอนเสนอแผน ไม่ต้องถามทีละจุดขณะเก็บ input (Step 0) เพื่อไม่ให้ผู้ใช้ต้องตอบคำถามกระจัดกระจายหลายรอบ

---

## Step 4 — สร้างไฟล์จริง (delegate ให้ subagent)

เมื่อผู้ใช้ยืนยันแผนแล้ว:

1. สร้างโฟลเดอร์ `prototypes/vN/` ตามที่ตัดสินใจไว้ใน Step 2 (ถ้าเป็นการแก้ version เดิม ก็ใช้ path เดิม)
2. เขียน `prototypes/vN/BUILD-PLAN.md` เก็บแผนที่ยืนยันแล้วทั้งหมด (ใช้เป็น context สำหรับรอบถัดไปที่จะมาแก้/ต่อยอด version นี้)
3. เรียก subagent `prototype-builder` (ผ่าน Agent tool, `subagent_type: prototype-builder`) พร้อมส่ง context ให้ครบ:
   - เนื้อหา `DESIGN.md` ทั้งหมด
   - Build Plan ที่ยืนยันแล้ว (โครงสร้างหน้า, feature ที่ต้องมี, user journey ที่ต้อง map)
   - Path ปลายทาง (`prototypes/vN/`)
   - ถ้าเป็นการแก้ version เดิม: ระบุชัดว่าไฟล์ไหนมีอยู่แล้วบ้าง และอะไรคือส่วนที่ต้องแก้/เพิ่มเท่านั้น (ไม่ต้องสั่งให้เขียนทับทั้งหมดถ้าไม่จำเป็น)
4. รอผลจาก subagent แล้วตรวจสอบคร่าวๆ ว่าไฟล์ถูกสร้างครบตามแผนก่อนสรุปให้ผู้ใช้

---

## Step 5 — สรุปผลให้ผู้ใช้

หลัง subagent สร้างไฟล์เสร็จ สรุปให้ผู้ใช้ทราบ:

- Path ของ prototype ที่สร้าง/แก้ (`prototypes/vN/`)
- รายชื่อหน้า/ฟีเจอร์ที่ทำเสร็จ
- วิธีเปิดดู (เปิด `index.html` ในเบราว์เซอร์ หรือใช้ Browser preview tool ถ้ามี dev server)
- ถ้ามี assumption ที่ตัดสินใจไปเองระหว่างทาง (นอกเหนือจากที่ถามใน Step 3) ให้ระบุด้วย เพื่อให้ผู้ใช้ตรวจทาน

แจ้งด้วยว่าถ้าต้องการปรับต่อหรือเพิ่ม requirement ใหม่ ให้เรียก skill นี้ซ้ำได้เลย ระบบจะถามเรื่อง version ให้อัตโนมัติ (ตาม Step 2)
