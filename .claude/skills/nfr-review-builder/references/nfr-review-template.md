# Template — NFR-REVIEW.md

ใช้เป็นโครงเริ่มต้นเวลาเขียน/แก้ `docs/02-design/02-technical/NFR-REVIEW.md` — ตัดหมวดที่ Build Plan ไม่รวมได้ตามจริง

---

## 1. ขอบเขตการ Review

- **Scope**: ทั้งระบบ หรือเฉพาะ Phase/component ไหน (จาก Build Plan)
- **หมวด NFR ที่ครอบ**: ระบุตามที่ยืนยันใน Build Plan
- **เอกสารที่ใช้เทียบ**: `HIGH-LEVEL-ARCHITECTURE.md` (มี/ไม่มี), `DATA-MODEL.md` (มี/ไม่มี), `API-SPEC.md` (มี/ไม่มี), `DETAILED-DESIGN.md` (มี/ไม่มี) — ถ้าไฟล์ไหนไม่มี ให้ระบุว่า "ยังไม่มีเอกสารนี้ ส่วนที่เกี่ยวข้องยัง review ไม่ได้"

## 2. ผลการ Review ต่อหมวด NFR

ต่อ 1 หมวด NFR ให้มีตารางแบบนี้:

### [ชื่อหมวด เช่น Performance]

| จุดที่ตรวจ | NFR ต้นทาง (อ้างอิงแหล่ง) | สถานะ | รายละเอียด |
|---|---|---|---|
| ... | ... | ✅ สอดคล้อง / ⚠️ ความเสี่ยง / 🔲 Gap (ไม่มีเป้าหมายกำหนดไว้) | ... |

**กติกาสถานะ**:
- **✅ สอดคล้อง** — เอกสาร design ที่มีอยู่ตอบโจทย์ NFR ต้นทางแล้ว ระบุว่าตอบโจทย์ตรงไหน (อ้าง diagram/ตารางที่เกี่ยวข้อง)
- **⚠️ ความเสี่ยง** — มี NFR ต้นทางชัดเจน แต่เอกสาร design ยังไม่ครอบ/ขัดแย้ง ระบุจุดที่ขัดแย้งให้ชัด
- **🔲 Gap** — ไม่มี NFR ต้นทางกำหนดไว้เลยในเอกสารใดๆ ของโปรเจกต์ **ห้ามตั้งเป้าหมายขึ้นเอง** ระบุว่าต้องสัมภาษณ์เพิ่มถ้าต้องการปิด gap นี้

## หลักการเขียนที่ต้องยึดเสมอ

- **ห้ามตั้งเป้าหมาย NFR เอง** — ถ้าไม่มีต้นทางในเอกสารโปรเจกต์ ต้องบันทึกเป็น Gap ไม่ใช่เดาตัวเลข/เกณฑ์ขึ้นมา
- **อ้างอิงแหล่งที่มาของ NFR ทุกครั้ง** — ระบุว่ามาจากไฟล์ไหน หัวข้อไหน เพื่อ traceability
- **Traceability กับ Feature ID** — ทุกจุดที่ review ควรโยงกลับ Feature ID/component ได้เท่าที่เป็นไปได้
- **ไม่แก้ไฟล์อื่น** — เป็นการ review เท่านั้น ไม่แก้ `HIGH-LEVEL-ARCHITECTURE.md`/`DATA-MODEL.md`/`API-SPEC.md`/`DETAILED-DESIGN.md` แม้จะพบ gap ก็ตาม (การแก้ไขเอกสารเหล่านั้นเป็นงานแยกที่ต้องเรียก skill ของเอกสารนั้น)
